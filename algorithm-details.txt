  4.2.1. Hybrid Recommendation Engine (Content-Based + Collaborative Filtering)

  The Recommendation Service implements a hybrid recommendation engine that combines Content-Based Filtering and Item-Item Collaborative Filtering to generate personalised product suggestions. This
  dual-signal approach directly addresses the two fundamental weaknesses of either method used in isolation — content-only systems create filter bubbles where users only see more of what they already
  interacted with, while pure collaborative systems fail entirely for new users who have no interaction history (the cold-start problem).

  Interaction Weighting

  Before computing recommendations, all user interactions stored in the analytics database are assigned differential weights based on the strength of intent they signal. A completed purchase carries a
  weight of 1.0, adding a product to the cart carries 0.7, a wishlist addition carries 0.5, and a product view carries 0.1. These weights reflect the confidence that an interaction represents genuine
  interest, and are used to scale a user's affinity toward products they have previously encountered.

  Offline Similarity Computation

  The computationally intensive portion of the engine runs offline as a scheduled background job, decoupled entirely from the HTTP request cycle. This is a deliberate architectural decision — computing
  recommendations at request time would introduce unacceptable latency.

  Content-Based Component: For each product in the catalogue, a feature vector is constructed from its structured metadata: category, subcategory, tags, brand, and normalised price range. Tags contribute
  the highest weight since they are the most semantically rich signal. Cosine similarity is then computed between all product pairs, producing a product-to-product similarity matrix. The cosine of the angle
   between two feature vectors captures how similar their characteristics are regardless of their individual magnitudes. The top-N most similar products for each item are persisted to Redis as a precomputed
   lookup table, enabling O(1) retrieval at serving time.

  Item-Item Collaborative Filtering Component: All user interaction records across the entire platform are loaded and used to construct an implicit interaction matrix where each cell represents whether (and
   how strongly) a user interacted with a product. For each pair of products, the algorithm computes a co-occurrence score — essentially counting how many distinct users interacted with both products,
  weighted by the strength of those interactions. This score is then normalised using cosine similarity over the interaction vectors. The result captures behavioural similarity: two products are considered
  similar not because of their attributes, but because the same population of users engaged with both. These scores are also persisted to Redis.

  Hybrid Serving

  At request time, the serving layer performs only lightweight read operations. Given a user's interaction history, the system retrieves the precomputed content-similar and collaboratively-similar product
  sets for each product the user has engaged with. Scores from both components are merged using a blending coefficient α, where the final score for a candidate product is computed as α × CF_score + (1 − α)
  × content_score. The value of α scales dynamically with the richness of the user's interaction history — users with sparse histories receive recommendations weighted toward content similarity, while users
   with rich histories receive recommendations increasingly driven by collaborative signals. After deduplication and filtering out products the user has already interacted with, the top-N results are
  returned.

  Cold Start Handling

  When a user has no interaction history whatsoever, both components produce no signal. In this case the engine falls back to a popularity-based ranking computed from each product's cumulative sales count
  and average rating, ensuring new users always receive a meaningful and commercially relevant set of recommendations rather than an empty response.

  4.2.6. Multi-Tier OTP Authentication with Redis-Backed Rate Limiting

  The authentication system implements a stateless, time-bounded One-Time Password (OTP) flow layered with a three-tier abuse prevention mechanism, all backed by Redis as the ephemeral state store. No OTP
  state is persisted to the primary database, keeping the authentication path fast and side-effect-free on MongoDB.

  OTP Generation and Delivery

  When a user initiates registration or login, a cryptographically random 4-digit integer is generated using a secure random number generator. This OTP is stored in Redis under a namespaced key tied to the
  user's email address, with a 300-second (5-minute) time-to-live. Redis TTL enforcement ensures OTPs are automatically invalidated without any scheduled cleanup job. Simultaneously, a 60-second per-request
   cooldown key is written to Redis to prevent repeated rapid requests.

  Three-Tier Abuse Prevention

  Before any OTP is issued, three Redis keys are checked in sequence and any positive result causes an immediate rejection:

  1. Account Lock — If a user has failed verification three or more times, a 30-minute hard lock is applied to their email. This limits brute-force attempts against a known OTP.
  2. Spam Lock — A rolling one-hour request counter tracks how many OTP generation requests have originated from the same email address. If this count exceeds two, a one-hour spam lock is applied. This
  prevents enumeration attacks and email flooding.
  3. Cooldown — A 60-second per-request rate limit prevents rapid successive requests within a single session.

  Verification and Lockout

  During verification, the submitted OTP is compared against the Redis-stored value. A failed attempt increments a counter with a 5-minute TTL. On the third failed attempt, the account lock from Tier 1 is
  activated, the OTP is deleted, and further attempts are blocked for 30 minutes. On success, both the OTP key and the attempt counter are deleted atomically, completing the flow cleanly.

  This architecture ensures that all OTP state is ephemeral, automatically garbage-collected by Redis TTL, and never touches the primary database — keeping authentication both secure and performant.

  4.2.7. Adaptive Low-Stock Alert System with Deduplication

  The platform implements an automated inventory monitoring system that runs as a scheduled background job, periodically scanning active product listings against per-seller configurable stock thresholds and
   dispatching multi-channel alerts when inventory falls critically low.

  Configurable Threshold Per Seller

  Each seller account holds a personalised lowStockThreshold value, allowing a high-volume electronics seller to set a higher minimum than a boutique artisan shop. The alert system respects this per-seller
  configuration rather than applying a platform-wide fixed threshold, making it commercially adaptable.

  Deduplication via Timestamp Guard

  A naive implementation would repeatedly alert a seller every hour for the same low-stock product until it was restocked — a significant source of notification fatigue. To prevent this, each product record
   stores a lastLowStockAlertAt timestamp. The query that identifies at-risk products includes a compound filter: the alert is only triggered if lastLowStockAlertAt is either null (never alerted) or older
  than 24 hours. This ensures each product generates at most one alert per day regardless of how many cron cycles execute.

  Dual-Channel Notification

  When a low-stock product is identified, the system simultaneously creates an in-app notification record in the database and dispatches a transactional email using a templated mail service. The email
  channel is governed by each seller's notification preference setting, which can be configured to email, web, app, or all. After dispatching, lastLowStockAlertAt is updated on the product, re-arming the
  24-hour guard.

  4.2.8. Dynamic API Rate Limiting with Role-Aware Thresholds

  The API Gateway implements a tiered rate limiting strategy that differentiates between authenticated and anonymous traffic, applying asymmetric request quotas to balance platform openness against abuse
  prevention.

  Sliding Window Counter

  Request counts are tracked using a 15-minute sliding window per client IP address. The IP is extracted from the request, respecting the X-Forwarded-For header in reverse proxy deployments to avoid
  incorrectly attributing all traffic to the gateway's IP.

  Dynamic Threshold Calculation

  Rather than applying a single platform-wide limit, the rate limiter evaluates the authentication state of each incoming request at runtime. Authenticated users are permitted up to 1,000 requests per
  15-minute window, reflecting their trusted and accountable status. Unauthenticated (anonymous) requests are capped at 100 per window — sufficient for browsing but restrictive enough to deter automated
  scraping and enumeration attacks. This dynamic threshold is computed per-request using a callback function that inspects the decoded user context attached to the request object.

  Client Feedback via Standard Headers

  Every response carries standard RateLimit-* headers indicating the client's current limit, remaining quota, and the timestamp at which their window resets. This enables client-side applications to
  implement preemptive back-off rather than relying on receiving a 429 error.

  4.2.9. Multi-Criteria Product Filtering and Sales-Weighted Ranking

  The product discovery layer implements a composable filter engine that translates user-facing filter selections into efficient database query predicates, combined with a ranking system that surfaces
  commercially relevant products.

  Composable Filter Construction

  Query parameters for price range, categories, colours, and sizes are parsed and dynamically assembled into a single compound database filter. Array-based attributes such as colours and sizes use
  set-overlap semantics — a product matches if it contains any of the selected values, not necessarily all of them. This mirrors natural shopping behaviour where a user searching for "red or blue" products
  expects results containing either. Price filtering uses bounded range predicates with sensible defaults when bounds are omitted.

  Dual-Mode Sorting

  Products can be retrieved in two ranked orderings. The latest mode sorts by creation timestamp descending, surfacing newly listed products — useful for returning users checking for new arrivals. The
  default topSales mode sorts by cumulative sales count descending, surfacing products with demonstrated commercial demand. Both modes are served with offset-based pagination.

  Top Shops by Revenue Aggregation

  A dedicated ranking pipeline aggregates all order records by shop, computing total revenue per shop through a grouped summation. The resulting ranked list is then enriched with full shop profile data,
  producing a leaderboard of the platform's highest-performing shops. This aggregation runs against the orders collection rather than product analytics, ensuring revenue rankings reflect actual completed
  transactions rather than interaction proxies.

  4.2.10. Idempotent Cart Session Management and Multi-Seller Order Partitioning

  The checkout flow faces two distinct algorithmic challenges: ensuring the server, not the client, is the authoritative source of pricing, and correctly splitting a single mixed-seller cart into separate
  per-seller orders.

  Cart Normalisation and Session Deduplication

  When a user initiates checkout, the server creates a validated payment session in Redis by fetching authoritative prices from the database and constructing a canonical session payload — the client's
  submitted prices are discarded. Before creating a new session, the system scans all existing active sessions belonging to the same user and performs a deterministic comparison. The cart is serialised into
   a normalised string (sorted by product ID to eliminate ordering variance) and compared against existing session payloads. If an identical cart and shipping address combination already has an active
  session, the existing session ID is returned rather than creating a duplicate. This prevents redundant sessions from accumulating when users navigate back and forward through checkout. Sessions expire
  automatically via a 10-minute Redis TTL, providing a natural cleanup mechanism.

  Per-Shop Order Partitioning

  Since the platform supports multiple sellers, a single user cart may contain products from several different shops. The order creation algorithm groups cart items by their shopId field, creating one
  independent order record per seller. This partitioning is essential for Stripe Connect payment routing, where each order's payment is transferred to the respective seller's connected Stripe account minus
  the platform's 10% fee. It also ensures that each seller's fulfilment, notification, and analytics pipelines operate on order data scoped exclusively to their shop.

  Discount Application with Ceiling Guard

  Coupon codes are validated against the specific product they were issued for, and discounts are computed differently depending on their type — percentage-based discounts are calculated proportionally
  against the item total, while flat discounts are applied directly. In both cases, a ceiling guard prevents the discount from exceeding the total price of the discounted item, ensuring order totals never
  go negative regardless of the discount configuration.

  4.2.11. Soft Delete with Grace Period and Scheduled Permanent Deletion

  The platform implements a two-phase deletion lifecycle for seller accounts and product listings, providing a recovery window before irreversible removal.

  Phase 1 — Soft Delete

  When a deletion is initiated, the record is not removed from the database. Instead, a boolean isDeleted flag is set to true and a deletedAt timestamp is written set to 28 days in the future for seller
  accounts. All active queries filter on isDeleted: false, making the record invisible to the application without destroying the underlying data. During this window, the deletion can be reversed by clearing
   the flag.

  Phase 2 — Scheduled Hard Delete

  A daily cron job runs at midnight UTC, querying for records where isDeleted is true and deletedAt is less than or equal to the current timestamp. Records that have crossed their grace period deadline are
  permanently deleted along with all cascading relations. This approach decouples the user-facing delete action from the irreversible storage operation, giving both users and platform administrators a
  recovery window without requiring any explicit restore scheduling.
